Top Recommendation

Deepen the Content Delivery API (CDA)

The cda-generator is currently shallow. It maps types and fetches data in a single pass, missing critical CMS features like relationship resolution, localized content, and nested block expansion. By extracting a QueryPlanner and ResolverFactory, we turn the CDA into a deep module that can handle complex content graphs.

1. Deepen GraphQL CDA Engine

src/app/api/graphql/_helpers/*

Strong

Problem

The CDA generation logic (cda-generator.ts) is shallow and tightly coupled to Supabase. It doesn't support complex relationships (e.g., fetching a "Post" and its "Author") or block-level content expansion.

Solution

Extract a CDACore engine. Move field resolution logic into dedicated **Resolvers** that understand relationship metadata and block structures.

Benefits

  • Leverage: Support complex relationship resolution once, use across all models.
  • Locality: Relationship fetching logic lives with the field definition, not the API route.
  • Depth: The interface (GraphQL Schema) stays simple while the implementation handles heavy graph traversal.

2. Formalize Registry Sync Observer

src/server/cms/adapters/supabase-schema-manager.ts

Worth exploring

Problem

The "Physical-Metadata Sync" described in CONTEXT.md is currently procedural. If a schema change fails halfway, the Registry can become out of sync with Postgres.

Solution

Introduce a SchemaCoordinator with a transactional SyncState. Treat schema changes as idempotent operations that can be re-run or rolled back.

Benefits

  • Interface as Test Surface: Tests can verify "Atomic Sync" by intentionally failing the Postgres update and checking the Registry.
  • Depth: Hides the complexity of DDL transactions behind a clean "UpdateModel" interface.
